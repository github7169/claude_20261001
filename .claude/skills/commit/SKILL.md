# Commit

변경사항을 읽고 의미 단위로 나눠, 일관된 한국어 메시지로 커밋한다. 커밋은 되돌리기 번거롭고 히스토리에 오래 남으므로, 실행 전에 사용자에게 계획을 보여주고 승인을 받는다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고
```

- git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 멈춘다.
- diff가 크면 파일 목록과 `git diff --stat`으로 먼저 윤곽을 잡고, 필요한 파일만 자세히 본다.
- `.env`, 키·토큰, 대용량 바이너리 등 커밋하면 안 될 파일이 보이면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 목적만 담는다. 나중에 `revert`나 리뷰가 쉬워지기 때문이다.

- 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 따로 나눈다.
- 같은 목적에 속한 코드와 그 테스트는 함께 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 나눌 수 있는지 검토한다. 어렵다면 하나로 묶고 이유를 설명한다.
- 변경이 하나의 목적뿐이면 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식: `타입: 요약`

| 타입 | 용도 |
|------|------|
| feat | 사용자에게 보이는 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 |

- 요약은 한국어로, 무엇을 했는지 한 줄(대략 50자 이내)로 쓴다. 마침표는 붙이지 않는다.
- "수정함"처럼 모호하게 쓰지 말고 대상과 결과가 드러나게 쓴다.
  - 좋음: `fix: 미리보기 새로고침 시 애니메이션이 리마운트되지 않는 문제 수정`
  - 나쁨: `fix: 버그 수정`
- 이유나 맥락이 diff만으로 드러나지 않을 때에 한해 빈 줄 뒤에 본문을 덧붙인다.
- 위 네 가지로 설명되지 않는 변경(테스트만 추가 등)은 가장 가까운 타입을 고르고, 저장소의 기존 로그가 다른 타입(`test`, `docs` 등)을 쓰고 있다면 그 관례를 따른다.

### 4. 사용자 승인

커밋하기 전에 계획을 다음 형태로 보여주고 승인을 기다린다.

```
커밋 계획 (2개)

1. feat: 프롬프트 예시 버튼 추가
   - src/components/ExamplePrompts.tsx
   - src/App.tsx
2. chore: eslint 규칙 업데이트
   - eslint.config.js
```

승인, 수정 요청, 거절 중 어느 쪽인지 사용자의 답에 따른다. 수정 요청이 오면 반영해 다시 보여준다. 승인 없이 커밋하지 않는다.

### 5. 커밋 실행

- 커밋마다 해당 파일만 명시적으로 `git add <파일>` 한다. `git add -A`나 `git add .`는 의도하지 않은 파일이 섞일 수 있어 쓰지 않는다.
- `git commit -m`으로 승인된 메시지를 사용한다. 여러 줄이면 heredoc을 쓴다.
- 현재 세션의 지침에 커밋 메시지 끝에 붙일 attribution(Co-Authored-By 등)이 있으면 그대로 따른다.
- `--no-verify`로 훅을 건너뛰지 않는다. 훅이 실패하면 원인을 보고하고 고친 뒤 새 커밋으로 만든다. `--amend`는 사용자가 요청할 때만 쓴다.
- 모두 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다. push는 요청받았을 때만 한다.
