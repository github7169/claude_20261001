# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.** 이 파일은 프로젝트별 규칙이 없을 때 쓰는 **기본값(fallback)** 이다. 두 규칙이 충돌하면 프로젝트 규칙을 따르고, 충돌하지 않는 부분은 이 파일을 따른다.

## 적용 기준

### TDD를 반드시 적용한다

- 비즈니스 로직
- API (핸들러, 요청/응답 처리, 에러 분기)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

판단이 애매하면 **로직(분기, 계산, 상태 변경)이 있는지**를 기준으로 한다. 있으면 적용한다.

## RED - GREEN - REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 실패했다면 테스트부터 고쳐 올바른 이유로 실패하게 만든다.

### GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구사항의 모든 동작이 테스트로 덮일 때까지 사이클을 반복한다.

## 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. 그 코드를 **삭제한다.**
2. **RED부터 다시 시작한다.**

**"참고용"으로 남기는 것도 금지한다.** 남겨둔 코드를 보고 테스트를 쓰면 구현에 맞춘 테스트가 되어, 테스트가 동작을 검증하지 못한다. 보지 않은 상태에서 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트가 불필요하다 | 단순한 코드는 테스트도 30초면 쓴다. 단순한 코드가 깨질 때 가장 늦게 발견된다. 테스트 비용이 가장 낮은 곳이다. |
| 나중에 테스트를 추가하겠다 | 나중에 쓴 테스트는 구현을 보고 쓰게 되어 이미 통과하는 것만 검증한다. 실패를 본 적 없는 테스트는 무엇을 잡는지 알 수 없다. 나중은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 회귀를 막아주는 테스트가 필요하다. |
| 삭제하면 낭비다 | 이미 쓴 시간은 매몰비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 테스트가 이끈 구현은 더 작고 빠르게 나온다. |
| 프로토타입이다 | 프로토타입은 살아남아 프로덕션이 된다. 버릴 코드라면 테스트도 가볍게 끝나고, 버리지 않을 코드라면 처음부터 필요하다. |
